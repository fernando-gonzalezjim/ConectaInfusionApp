# Account listing and personal profile edits

I17 implements opt-in account administration endpoints. Both frontends can use the same API; [management screens](identity-administration.md) are implemented in I19. [Role administration](identity-roles.md) is implemented in I18; self-profile/email screens and the email-change workflow are I20, photos are I21, and account lifecycle is a later task. Customer invitation creation remains the separate [I15/I16 workflow](identity-invitations.md).

| Endpoint | Input | Success |
| --- | --- | --- |
| `GET /api/v1/accounts` | Optional query `limit`, `cursor`, `role`, `status` | 200 `{ accounts, nextCursor }` |
| `POST /api/v1/accounts/:id/profile` | At least one of `fullName`, `phone`, `preferredLocale` | 200 account profile |

Only administrator/manager accounts can list accounts or update another account's personal details. Every active independent account can update its own profile, including customer, reception, cafÃ© staff and instructor roles. Ordinary personnel cannot edit another customer even if they invited that customer. Multiple roles use the combined current authority; the API never accepts actor IDs or roles from the body. A well-formed unknown target returns 404 to management but 403 to an ordinary actor attempting another-account access, without revealing whether the target exists.

Names are trimmed, required when supplied, and limited to 120 JavaScript UTF-16 code units, matching registration validation. Phones accept null or a string of at most 40 code units. Name and phone reject control characters. Preferred locale is `es-MX` or `en`. Extra fields are rejected, including roles, email, passwords, confirmation status, account/person identifiers, ownership, pay rates, lifecycle status and photo IDs. Email changes and photos use their separate security/upload workflows. Existing customer, personnel or instructor account roles never change through profile editing. Pending and inactive accounts may have their details corrected by management without activation or credential changes.

Listing defaults to 25 records and allows 1â€“50 per page. The UUID cursor follows ascending account ID; use `nextCursor` from the previous response, retaining the same filters. Pagination is bounded, deterministic traversal, not a frozen snapshot across requests. Optional `role` matches any assigned identity role; a multi-role account can appear under each applicable role filter. Optional `status` accepts `pending`, `active` or `inactive`. Unknown/repeated/invalid query parameters are rejected. Without filters, pending and inactive records are included for authorized management. Legacy instructor/member records without reviewed account links are not claimed or exposed by this endpoint.

Returned profiles include `id`, `personId`, email, full name, phone, preferred locale, photo ID, account status, profile status, confirmation status and roles. Password hashes, session state, confirmation/reset tokens, exemption reasons/actors and raw audit history are omitted. Photo ID is a read-only reference until the photo workflow is delivered. Profile edits update the canonical person record; instructor catalog/media/rates and financial records remain in their owning modules. Shared `AccountProfileInput`, `AccountProfile` and `AccountListResponse` contracts describe these responses.

The server resolves the session and rechecks account/profile activity, session version, revocation, expiration and current roles inside the transaction. Account/person locks use deterministic ID order; invitation resend follows the same account order. Future role/lifecycle mutations must follow that lock discipline. Expiration is evaluated after authorization locks. Target edits and before/after profile audits commit together; audit failure rolls back the edit. Audit actors are classified from current locked roles, and audit snapshots contain only the editable personal fields. Editing a name, phone or locale does not revoke sessions or alter credential/verification history.

Reads require an authenticated session and reject foreign Origin headers. Writes additionally require an exact configured Origin, JSON and session-bound `X-CSRF-Token`. Bodies are limited to 2 KB and all account responses use `Cache-Control: no-store`. Failures return stable codes: `INVALID_REQUEST` (400), `UNAUTHENTICATED` (401), `FORBIDDEN` (403), authorized missing target `NOT_FOUND` (404), or generic `UNAVAILABLE` (503). These endpoints do not hard-delete records, reactivate accounts or implement family/guardian access.

For local API testing, follow [identity configuration](identity-local-email.md) and [bootstrap](identity-bootstrap.md), then sign in normally and use the session cookie and CSRF token. Management can read `/api/v1/accounts?role=customer&limit=25`. A profile mutation body such as `{ "fullName": "Updated name", "preferredLocale": "es-MX" }` applies only to the authorized target. I19 provides management screens and browser verification; I20 provides [own-profile editing and verified email changes](identity-profiles.md) in both frontends. I17 verification uses real PostgreSQL and HTTP requests against disposable fixtures.
