# Role administration

I18 provides `POST /api/v1/accounts/:id/roles` for active administrators and managers. The [I19 administration screen](identity-administration.md) is available on the management frontend. Send `{ "roles": ["customer", "instructor"] }` with a valid session, exact configured Origin and session-bound `X-CSRF-Token`. JSON bodies are bounded to 2 KB; responses use `Cache-Control: no-store`.

Supported roles are `administrator`, `manager`, `reception`, `cafe_staff`, `instructor` and `customer`. The request requires one to six distinct roles and rejects extra fields. Ordinary staff, instructors and customers cannot change anyone's roles, including their own. Pending and inactive targets return `CONFLICT`; pending invitations remain customer-only until setup completes. Unknown targets return 404 only after management authorization.

An existing customer role is retained automatically when changing personnel roles. Retained assignments preserve their original provenance. An identical assignment is a no-op: it does not revoke sessions, increment versions or add an audit event. Actual changes revoke every target session, increment its session version and atomically record sanitized before/after roles with the current actor. The response contains only `accountId`, `roles` and `staffAttendanceEligible`. The latter describes future free-attendance eligibility; it does not implement bookings or instructor payments.

The transaction serializes administrative removals with the `identity-active-administration` advisory lock before ordered account, person, session and role locks. It rechecks current authority and session validity after waits. Removing the last login-eligible active administrator or manager returns 409 `CONFLICT`. Eligibility requires an active person/account, a supported password hash and verified or explicitly exempt email. Development fixtures count only under the same opt-in development/database guards used by login; copied production fixtures do not count. Future account lifecycle operations that can remove administrative access must take this advisory lock before account locks.

Loss of personnel eligibility or removal of the instructor role requires domain coordination. A trusted composition hook receives the same PostgreSQL transaction and before/after roles; any failure rolls back role, session, audit and coordinator writes. Until booking/scheduling/payroll coordination exists, the default guard fails closed on any legacy booking, linked member, linked instructor, unlinked instructor, or unknown public table outside the reviewed Foundation/Identity schema. This deliberately broad temporary guard can block unrelated legacy obligations; it must not be treated as proof that those obligations belong to the target. No bookings, credits, sessions taught or payroll records are silently deleted or reassigned. Later integration will replace these conservative conflicts with verified domain-specific coordination.

I23 adds `families` and `family_memberships` to the reviewed Identity schema. Their presence alone does not block personnel-role changes: existing customer access and family history/membership remain intact. This does not exempt future credit, booking or other unknown domain tables from the conservative guard.

Other stable failures are `INVALID_REQUEST` (400), `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404) and generic `UNAVAILABLE` (503). Use the [account guide](identity-accounts.md) to locate an account and [bootstrap guide](identity-bootstrap.md) for development access. Account lifecycle and instructor catalog/rates remain separate planned tasks.
